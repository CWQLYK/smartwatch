## 三、实施中的偏离与"意外收获"（逐条说明）

### 3.1 A1：验证方式比计划更硬 —— 去掉修复后模拟器直接崩

计划里只写"加一个定时器数不变的断言"。实际做的时候多走了一步：把修复用 `git stash` 临时移除再跑，
结果是**进程访问违例（0xC0000005）**，而不是"断言失败"。

```
有修复：WiFi 扫描中关闭  关时在扫描=1  定时器 6 -> 6  OK
无修复：自检退出码 = -1073741819（0xC0000005 访问违例）
```

这说明两件事：① 这个 P0 是**真的**（不是"理论上可能"）；② 该用例确实能抓住它。
修复后 `page_delete_cb` 在 `wifi_page_build()` 里用 `remove+add` 挂载，页面被销毁时删定时器并清指针。

### 3.2 A5：把"吞掉唤醒那一下"放到平台层，并顺手修了模拟器的一个假实现

- 状态放在 `watch_platform.c`（不是 `bsp.c`）——因为 **bsp 只有手表端编译**，放平台层模拟器才能测。
- 写测试时发现 **模拟器的 `sim_screen_activity()` 是个空实现**：屏幕灭着时根本不会亮，
  于是"息屏→触摸→亮屏"这条路径在模拟器里永远走不到，A5 这类 bug 也就测不出来。
  已改成与实机 `power.c` 的 `hook_activity()` 同语义。
- 去掉修复跑一遍：`吞掉=0 ... **异常**`、退出码 1 → 断言有效。

**边界（诚实说明）**：自检验证的是"平台层置位/解除 + 界面未被误触发"；
`bsp.c` 里"上报改 RELEASED"那 3 行只有手表端编译，**端到端效果需要实机确认**（见第六节第 1 条）。

### 3.3 A6：方案改了两次，第二次才对

- 原计划：把 3 处 `lv_obj_del` 改成 `lv_obj_del_async`。
- 先核实了 LVGL 源码，确认这**不是**理论风险：`_lv_event_mark_deleted()` 只在"被删对象**就是**事件 target"时置位
  （`lv_event.c:147-155`），而事件循环返回后仍要解引用 `e->current_target`
  （`lv_event.c:449/454/469`，以及 `:472` 读 `->parent`）→ 删祖先 = 读已释放内存。
- **第一次实施（错的）**：把游戏的面板和根**都**改成异步删。模拟器立刻崩在"游戏已退出"之后 ——
  因为 `lv_async_call` 是各建一个 0ms 一次性定时器，**两个延迟删除的执行顺序不保证**；
  若根先删，面板那条延迟回调就会去动已释放内存（`lv_obj_del_async_cb` 是无条件 `lv_obj_del(obj)`，
  见 `lv_obj_tree.c:344-349`）。
- **最终方案**：模态侧保持"先隐藏 + 异步删根"（单次延迟删除，无顺序问题）；
  游戏侧**不动收尾逻辑**（保持同步删），改为在事件回调入口 `cb_quit()` 里
  `lv_async_call(cb_quit_deferred, NULL)` —— 整个收尾挪到事件派发之后执行，从根上消除"回调里删祖先"。

> 教训记在这里：**同一个对象树上不要排两个延迟删除**。这条已写进 `panel_clear()` 的注释。

### 3.4 A7：按屏幕高算错了，实际要为"页面内边距"留 24px

计划的算法是 `280 - 32(标题) - 5×h - 4×gap`。**错了**：页面根有 `pad_all = W_PAD_PAGE(12)`
（`watch_widgets.c:32`），内容区只有 **256px**。

第一次改成 46px，自检立刻报：

```
功能列表可滚 22 px（期望 0）  **内容又溢出了，第 5 行会看不到**
功能列表布局  行数 5，末行底部 y=289（屏高 280）
```

22px 正好是一个上下 padding（12+10），于是改成 **行高 43 + 间隙 2 + 列表上移到 28**：

```
功能列表可滚 0 px（期望 0）  OK（5 行一屏放下）
功能列表布局  行数 5，末行底部 y=262（屏高 280）  OK（第 5 行完整可见）
```

行内纵向内边距从 10 压到 2（`lv_obj_set_style_pad_ver(card, 2, 0)`），否则两行字会叠。
**模拟器截图已确认不叠字**（`lvgl_sim/shot_functions_all_rows.png`），但**观感请你在实机确认**。

同时把 v0.6.0 那条"这一页必须能滚"的断言**反转**成"不该再滚"，
并新增真正的契约断言"末行必须完整在屏内" —— 以后谁把行高改回去，自检会立刻报警。

### 8.1 新发现并修复：连接失败被误判成"用户主动断开"（P1）

**现象**：连 `CWQLYK` 一直失败，日志只有：

```
I WIFI: 使用已保存的密码重连 'CWQLYK'（8 位）
W WIFI: 等断开事件超时，仍然继续配置
I WIFI: 正在连接 'CWQLYK'…
I wifi:state: init -> auth (0xb0)
I wifi:state: auth -> init (0x200)          ← 4.2 秒后认证超时
W WIFI: 断开（reason=2）
I WIFI: （用户主动断开，保持未连接状态）      ← ★ 误判
I WIFIPAGE: 状态 1 -> 0，重建页面            ← 界面看不出任何错误
```

**根因**：`hook_connect()` 在 `esp_wifi_disconnect()` 前**无条件**置
`s_user_disconnect = true`（指望"紧随其后的断开事件把它消费掉"）。
但**断开一个空闲的站点根本不会产生事件** —— 日志里"等断开事件超时"就是这种情况。
于是标志一直留着，把 4 秒后**真正的认证失败**事件当成"用户主动断开"：

- 状态回 `IDLE` 而不是 `FAILED` → 界面**不报错**
- 跳过"清理坏凭据"的分支 → **下次还是拿同一个旧密码去连**

结果：永远连不上、永远不提示、也永远不重新问密码 ——
v0.5.0 专门写的"密码错就自动取消保存并重新询问"补救逻辑**永远不触发**。

**实测判据（关键实验）**：用**故意错误的密码** `00000000` 连同一个 AP，
得到**完全相同的 `reason=2`**：

```
I (5167) wifi:state: init -> auth (0xb0)
I (9405) wifi:state: auth -> init (0x200)
W (9409) WIFI: 断开（reason=2）
```

说明这个 AP（扫描显示 `authmode=7` = **WPA2/WPA3 过渡模式**，`rssi=-29` 信号极好）
在 SAE 流程下**密码不对的表现就是 reason=2**。

**修复**（`wifi_service.c` 4 处）：
1. 新增 `disconnect_event_expected()`：只在"确实连着/正在连"时才认为会有断开事件；
2. `hook_connect()` / `hook_disconnect()` / `hook_forget()` / `wifi_service_reset()`
   由无条件 `= true` 改为用该判定；
3. `hook_connect()` 等完 2 秒窗口后**一律清掉标志**，不让它漏给后面的失败事件。

**修复后真机复测（同样的坏密码）**：

```
W (10545) WIFI: 断开（reason=2）
W (10545) WIFI: 用已保存的密码连接失败（reason=2）-> 清除保存的凭据，下次会重新询问密码   ✅
```

`wifi status` 确认：`已保存凭据: （无）`、`自动重连=否` → **恢复路径通了**。

> ⚠️ **必须交代的一件事**：我做"错误密码"实验时，那次 `wifi connect` 把 `00000000`
> 写进了 NVS（`hook_connect` 在设好配置后会保存凭据），随后这次修复又把它清掉了。
> 所以现在表里**没有任何已保存密码**，需要**重新输入正确密码**。
>
> ⚠️ **我无法从设备侧证明**原来存的 `42516911` 是错的 —— 因为"密码错"与
> "AP 拒绝我们的认证"在这个 AP 上都表现为 reason=2。判定方法：**用正确密码再试**。
> 若仍 reason=2，则不是密码问题，下一步查过渡模式兼容性（`pmf_cfg` / `sae_pwe_h2e`，
> 必要时强制走 WPA2）。

### 8.2 A9 `taskmem` 实测（栈余量，单位字节）

```
console_repl 4800 | IDLE0 696 | IDLE1 688 | motion 2056 | data_hub 2048
tiT 2420 | main 5744 | taskLVGL 3328 | Tmr Svc 1336 | settings_ev 1024
sys_evt 1628 | ipc1 508 | wifi 4328 | esp_timer 2100 | ipc0 500
```

结论：
- **`data_hub` 的 4096 是合适值**：余 2048 → 峰值用了 2048。
  反推：v0.6.1 之前的 3072 只剩约 1KB 余量，确实偏紧（提到 4096 的决定是对的）。
- **没有任何任务余量低于 512 字节** → 当前没有栈溢出风险。
- 最紧的非系统任务是 `settings_ev`（余 1024）。
- `taskLVGL` 余 3328（给 6144）偏宽，但**不建议现在缩**（收益小、风险不值当）。

### 8.3 A10 coredump 实测（完整链路打通）

### 8.5 WiFi 深入排查（用户确认密码无误之后）

用户确认密码 `42516911` **确实是对的**，但仍然 `reason=2`。于是继续做实验，两条关键结果：

**① 反证：我们的认证通路正常。**
用（故意写错的）密码去连附近一台**纯 WPA2** 的 AP，它一路走完了：

```
I wifi:state: auth -> assoc (0x0)
I wifi:state: assoc -> run (0x10)
I wifi:connected with ZTE-dxbP9F, channel 13, bssid = b4:72:d4:7d:cf:77
I wifi:security: WPA2-PSK, phy: bgn, rssi: -67, cipher(pairwise:0x3, group:0x3), pmf:0
```

⇒ 认证 / 关联 / 4 次握手 / DHCP 这条链路本身没问题。

**② 负结果：不是 WPA3-SAE 的问题。**
把 `CONFIG_ESP_WIFI_ENABLE_WPA3_SAE=n`（强制 WPA2-PSK）烧进去实测 —— **仍然 reason=2**。
而且此时该 AP 的状态已经变了（见下）。⇒ 已把这个实验**回退**（SAE 恢复默认开启，
关掉只会白白失去连纯 WPA3 AP 的能力），并在 `sdkconfig.defaults` 里留了结论注释。

**③ 排查中发现该 AP 的配置被改过：**

| 时间 | 扫描结果 |
|---|---|
| 最初 | `CWQLYK authmode=7(WPA2/WPA3) ch=11 rssi=-29` |
| 后来 | `CWQLYK authmode=**3(WPA2)** ch=**6** rssi=-26` |

信道从 11 变到 6、加密从"WPA2/WPA3 过渡"变成"纯 WPA2" —— 而**在纯 WPA2 状态、
SAE 已关、密码正确、信号 -26dBm 的条件下依然 `reason=2`**。

**④ 结论（证据链完整）**：

> **认证阶段是"开放系统认证"，跟密码、PMF、WPA3 都无关** —— AP 收到就该回应。
> 我们的认证帧能被别的 AP 正常受理（见 ①），而 CWQLYK 在正确信道、极好信号下
> **完全不回应**。⇒ **问题在 AP 侧**：它在按 MAC 或容量过滤客户端。

**⑤ 下一步在路由器上（需要你做）**：

手表的 WiFi MAC 是 **`a0:f2:62:e4:c1:28`**（从启动日志 `wifi:mode : sta (...)` 取的）。
请依次检查：

1. **MAC 地址过滤 / 白名单**（最可能）：把这个 MAC 加进去，或先把该功能关掉试一次；
2. **最大客户端数 / 带机量**：路由器是否已经连满（有些机型满了就静默忽略新认证）；
3. **"防蹭网"/"仅允许已连接过的设备"**这类开关；
4. **双频合一 / 访客网络隔离**：可临时把 2.4G 单独设个不同 SSID 试；
5. **重启路由器**：如果它现在处于半异常状态（配置被改过、信道跳过），重启是廉价的排除法；
6. 对照：**手机现在能正常上网吗**？路由器管理页的客户端列表里有没有它？

> 若以上都排除后仍然连不上，下一步我会给 WiFi 驱动开 DEBUG 日志
> （能看到"发出认证帧 → 对面有没有回"的 802.11 层细节），那是最硬的证据。

**⑥ 结果：用户重输一次密码就连上了（2026-10-08，已实机确认）**

用户反馈"**没改路由器，重新输入一次密码就好了**"。—— 这与 ⑤ 的推测不一致，
所以按事实更正记录：

- **已确认**：WiFi 现在正常工作（用户实机确认；本次未再复现失败）。
- **未唯一确定**：到底是"当时那台 AP 处于瞬时异常"（它自己改过加密方式与信道，见 ③），
  还是"用户这次输入的口令与此前存进 NVS 的那串不同"。
  - 关键事实：我在 ④ 之前用 `wifi connect CWQLYK 42516911`（**绕开 NVS、直接给口令**）
    试过两次（SAE 开 / 关各一次）都失败。若那串口令正确且 AP 当时正常，本应成功 ——
    所以"AP 当时不正常"与"那串口令其实不对"两者必有一个成立。
  - **一行命令即可定论**（等串口空闲时做）：让表用 NVS 里保存的密码重连，
    日志会打印 `密码字节码`，与 `34 32 35 31 36 39 31 31`（= `42516911`）比对即可。
- **8.1 那个修复的实际价值（与上面无关，独立成立）**：
  它在认证失败时**清掉了保存的凭据**，于是用户被"逼"着重新输了一次密码。
  也就是说 **没有这个修复，那条死循环会一直存在**（一直拿存着的口令重试、
  既不报错、也不给改的机会）。它起的正是该起的作用，只是生效路径比预期曲折。

> **记录原则：没有证据的部分不写成结论。**
> ⑤ 里"AP 按 MAC 过滤"只是当时证据下**最可能的解释**；既然现在出现了反证
> （用户没动路由器、重输密码就好了），就不把它留作结论。本节如实保留两种可能。

| 位置 | 问题 |

### 8.7 追加修复：凭据只在"真的连上"之后才落盘（已实测验证）

**问题**（§8.6 第 2 条）：`hook_connect()` 在"配置刚写进驱动"时就 `creds_save()`，**根本没等连上**。
后果：**密码打错也会被写进 NVS**，把原本能用的那个顶掉 —— 手滑输错一位，好密码就没了。
（这不是理论：排查 WiFi 时我自己用错误密码连了一次，NVS 里随即变成那个错密码。）

**改法（两段式）**：

| 时机 | 行为 |
|---|---|
| `hook_connect()` 里 | 只把凭据**暂存**到 `s_pend_ssid/s_pend_pass`，**不落盘**（`pend_clear()` 先清旧暂存） |
| `WIFI_EVENT_STA_CONNECTED`（关联 + 4 次握手都过了 = 密码对） | 才真正 `creds_save()`；成功则 `auto_reconnect = true` |
| `WIFI_EVENT_STA_DISCONNECTED`（失败 / 用户主动断开） | 丢掉暂存：`连接未成功 -> 本次凭据不写入 NVS` |
| `hook_forget()` / `wifi_service_reset()` | 一并清暂存（否则刚"忘掉"的网络会被写回去） |

v0.5.0 那三条规则（用 `eff_pass` 不用入参、空密码不写、开放网络只记 SSID）**一条没动**，
改的只是"什么时候写"。暂存区用完立刻 `memset` 清掉（别把明文密码留在 RAM 里）。

**真机验证（两条路径都验了）**：

```
# ① 失败路径：故意错密码
$ wifi connect CWQLYK 00000000
W WIFI: 断开（reason=2）
W WIFI: 连接未成功 -> 本次凭据不写入 NVS
$ wifi status
I WIFI:   已保存凭据: （无）                      ← ★ 错密码不再污染 NVS

# ② 成功路径：连另一台 AP（顺带又做了一次"我们的链路正常吗"的对照）
$ wifi connect ZTE-dxbP9F 00000000
I wifi:state: auth -> assoc (0x0)
I wifi:state: assoc -> run (0x10)
I wifi:connected with ZTE-dxbP9F, channel 13, ... security: WPA2-PSK
$ wifi status
I WIFI:   已保存凭据: ZTE-dxbP9F                 ← ★ 只有连上了才存
```

**顺带又确认了一遍：`CWQLYK` 那台现在仍在拒绝我们**
（用 `42516911` 与错误密码表现完全相同，都是 `reason=2`；同一时刻别的 AP 一切正常）。
⚠️ 而且为了跑这个验证，我执行了 `wifi reset` —— **把表里那份"能用的凭据"清掉了**，
需要重新输一次密码（这也正好是钉死该悬案的机会：连上后跑 `wifi connect <SSID>`（不带密码），
日志会打印 NVS 里那份密码的**字节码**，可用来核对到底存的是什么）。
