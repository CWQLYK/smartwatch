## 一、这一版解决的实际问题

三件事驱动了本版本：

1. **计步参数调不了**：USB 线太短，只能坐着甩手，而甩手和走路的信号特征
   完全不是一回事。必须让手表自己录数据。

## 一之二、🔴 用户实测反馈的 Bug：设置页滚不动，"开发人员选项"够不着

> 这一条是**用户上手后报的**，不是我自己发现的。记录完整过程。

### 现象

设置页看不到"开发人员选项"，而且**上下滑动没反应**。

### 根因（两个问题叠加）

**问题 1：内容确实超出屏幕，但页面不能滚**

算一下设置页的布局账：

| 行 | y 范围 |
|---|---|
| 亮度卡（滑块） | 26 .. 82 |
| 自动息屏 | 88 .. 128 |
| 抬腕亮屏 | 134 .. 174 |
| 步数目标 | 180 .. 220 |
| 身高 | 226 .. 266 |
| **体重** | **272 .. 312** ← 已出屏 |
| **时钟状态** | **318 .. 358** |
| **WiFi 连接** | **364 .. 404** |
| **开发人员选项** | **410 .. 450** |

内容总高 **450px**，屏幕只有 280px，**超出 170px**。
而 `w_page_create()` 里明确写着：

```c
/* 页面根**不可滚动**：跟手滑动靠外层 viewport 来滚 */
lv_obj_clear_flag(root, LV_OBJ_FLAG_SCROLLABLE);
lv_obj_set_scroll_dir(root, LV_DIR_NONE);
```

外层 viewport 只滚**水平**方向（轮播），垂直方向**没人管**。

**问题 2：纵向拖动被直接丢给"上滑开控制中心"**

```c
/* watch_pages.c: on_pressing */
if (LV_ABS(dx) <= LV_ABS(dy)) {
    return;      /* 纵向留给手势层（上滑控制中心）*/
}
```

所以纵向拖动**永远不会滚页面**，只会去开控制中心。

**这是我的设计疏忽**：我做轮播时假设"页面内容都不超过一屏"，
结果设置页加到 9 行就超了。而且我在 v0.4.0 文档里
只把它标成"没自动滚动"，低估了严重性 —— 实际是**功能完全够不着**。

### 修法（以及为什么不用"让页面自己滚"这个看起来最顺的方案）

**第一版尝试**：把页面根改成 `scroll_dir = LV_DIR_VER`，让 LVGL 自己滚。

看起来完美，而且有个额外好处：LVGL 在 `lv_indev.c:1121` 有

```c
static void indev_gesture(...)
{
    if(proc->types.pointer.scroll_obj) return;   /* 滚动时就别发手势了 */
```

也就是说"页面能滚"时手势层的纵向判定会自动不触发，
不用额外写判断。

**但这个方案有个致命副作用**（读 `lv_indev_scroll.c: find_scroll_obj` 才发现）：

> 一旦对象是 `SCROLLABLE`，它就会被当成滚动候选 ——
> **即使内容根本没超出**（LVGL 要留它做弹性回弹效果）。

后果：**内容不满一屏的页面（表盘/健康/运动）也会设置 `scroll_obj`**，
于是 `indev_gesture()` 直接 return，
**"上滑打开控制中心"在整个手表上就全废了**。

**最终方案**：页面根保持不可滚动，纵向滚动**由轮播显式代管**：

1. `watch_pages.c` 加 `current_page_scroll_range()`：
   临时借一下 `SCROLLABLE` 标记，问 LVGL"下面还有多少内容"，问完立刻还回去
2. `on_pressed()` 里算一次缓存在 `s_page_scroll_limit`（别每帧都查布局）
3. `on_pressing()` 里：主轴是纵向**且** `s_page_scroll_limit > 0`
   → 用 `lv_obj_scroll_by_bounded()` 滚当前页；否则照旧交给手势层
4. `rebuild_window()` 里把新页滚回顶部（否则换页后会停在上一页的残留滚动位置）

这样：
- **内容溢出的页面** → 纵向拖动滚页面，上滑不会误开控制中心
- **内容不满一屏的页面** → 纵向拖动照旧上滑开控制中心

### 验证（实机，用新加的 `pages` 命令查）

| 页面 | 可纵向滚动 | 行为 |
|---|---|---|
| home 表盘 | 0 px | 上滑开控制中心 ✅ |
| **settings 设置** | **194 px** | 纵向拖动滚页面 ✅ |
| health 健康 | 0 px | 上滑开控制中心 ✅ |
| sport 运动 | 0 px | 上滑开控制中心 ✅ |

194px > 170px（超出量），所以**能滚到底，开发人员选项够得着了**。

### 修完之后又反了一次：拖动方向相反（用户实测反馈）

第一版修好"能滚"之后，用户反馈**能拖了但方向是反的**（下拖看到上面的内容）。

**原因**：我在 `scroll_page_by()` 里写成了 `lv_obj_scroll_by_bounded(page, 0, -dy, ...)`，
那个负号是想当然加的（"手指往下、内容往上，所以取负"）—— 推错了一层。

**LVGL 的真实约定**（读源码确认，不是猜的）：

```c
/* lv_obj_scroll.c */
lv_coord_t lv_obj_get_scroll_y(const lv_obj_t * obj) {
    return -obj->spec_attr->scroll.y;      /* 注意这个负号 */
}
lv_res_t _lv_obj_scroll_by_raw(lv_obj_t * obj, lv_coord_t x, lv_coord_t y) {
    obj->spec_attr->scroll.x += x;
    obj->spec_attr->scroll.y += y;         /* 直接累加 */
    lv_obj_move_children_by(obj, x, y, true);
```

所以 `scroll_by(+dy)` → `scroll.y` 变负 → `scroll_y` 变大 → **内容上移**，
也就是"手指下拖看到更下面的内容"—— 正是所有触屏系统的标准行为。
而 `lv_indev_scroll.c` 里手势滚动用的就是
`lv_obj_scroll_by(obj, diff_x, diff_y, ANIM_OFF)`，**diff_y 直接取自输入向量，没有任何取反**。

**修法**：把 `-dy` 改成 `+dy`，并在代码里写清楚依据，免得以后又"顺手"加个负号。

> 教训：自己推坐标系很容易错一层。**能读源码确认的就别猜** ——
> 这次是去读 `lv_obj_get_scroll_y` / `_lv_obj_scroll_by_raw` / `scroll_y_anim`
> 三处才把符号钉死的。

### 新增的排查工具

```
pages        当前页的可滚动量 / 水平偏移 / 槽位坐标
next         翻到下一页（调试用，实机靠滑动）
```

> 以后再遇到"某个按钮在屏幕外够不着"，先跑 `pages`：
> 数字 > 0 说明**应该**能滚（那问题在拖动处理），
> = 0 说明是**布局没溢出但控件被放错位置**（问题在布局代码）。
> 这一条能省掉一半的排查时间。

## 一之三、🔴 用真实走路数据标定计步参数（原参数完全不能用）

> 用户录了第一份**真实走路数据**后发现的。这是"必须先做 IMU 录制"这个决定
> 最直接的回报 —— 不录真实数据，这个 bug 永远发现不了。

### 现象

真实数据：**50 步 / 40.6 秒（74 步/分）**，算法输出 **0 步**。

### 排查（逐层剥）

写了个把 C 定点实现**逐行照搬**到 Python 的离线仿真器
（`tools/step_tune.py`），拿真实数据反复跑 —— 在设备上试一次要
编译+烧录+带表走 50 步+导出，Python 里几秒一轮。

第一层：检测到 **475 个候选峰，444 个被"波峰因数门"拒绝**。

第二层：把门限和 σ 打出来 ——

```
peak_q10 : 中位 226
sigma_q10: 中位 146      ← 和 peak 同一个量级
crest 门 : 要求 peak >= 2.0 × sigma = 292
→ 只有 31/475 个峰能过
```

第三层：看信号本身 —— **根因在这里**。

```
|bp| 均值 120 Q10，p95 = 300，峰值 545     ← 信噪比其实很好
σ ≈ 146                                    ← 和 |bp| 均值同量级
```

也就是说**信号不是脉冲型的，而是一个很强但很平滑的正弦**。
原因很直白：用户走 74 步/分 = **1.23Hz**，正好落在带通的中心频率
（BPF f0 = 1.323Hz）。腕部在这种速度下就是平滑摆动，没有足跟冲击的尖峰。

而 `crest_min_x100 = 200`（"峰值 ≥ 2.0σ"）这个判据的设计前提是
**"步态冲击是脉冲型，平滑摆动不是"** —— 在合成模型上成立，
在真实腕部的带通中心频率上完全不成立。

第四层：原始峰之间的间隔直方图，暴露了第二个问题 ——

```
原始 92 个峰（关掉所有拒绝门）：
   100-199ms : 26 个   ← 一步双检
   200-299ms : 15 个   ← 一步双检
   300-399ms : 16 个   ← 一步双检
   700-1200ms: 20 个   ← 真实步（真值 50 步 / 40.6s，平均步周期 812ms）
```

**57 个双检**。原因是信号平滑 + 自适应门限贴着信号走，
一个步周期内会反复穿越门限，峰值跟踪被反复"闭合→重新武装"。

### 修法（三个参数）

| 参数 | 原值 | 新值 | 理由 |
|---|---|---|---|
| `crest_min_x100` | 200 | **0（关闭）** | 真实腕部信号是平滑正弦，这个门会拒掉真实步。改用不应期+步频+节律压误计 |
| `refractory_ms` | 250 | **400** | 挡住 100-400ms 的一步双检；又留给 150 步/分（400ms 周期）的快步 |
| `cadence_min_spm` | 60 | **50** | 实测 74 步/分，原下限对慢走太苛刻 |
| `rhythm_cv_x1000` | 260 | **700** | 配合上面三项，放宽节律门以补偿 |
| `peak_thresh_mg` / `start_thresh_mg` | 60 / 60 | **50 / 60** | 真实峰值中位 226 Q10，地板可以低一点 |

### 标定结果

```
真实数据：      50 步 -> 51 步   （误差 +2.0%）
合成交叉检查：  60~120 步/分 最差 2.1%   （原来 100%）
```

拒绝统计也变得合理了：`near=43`（挡掉的正是那些一步双检），
`crest=0`（门已关闭），`rhythm=3`。

### ⚠️ 为什么不敢说"调好了"

**只有一份真实数据**，而且只有 40 秒、一个步频（74 步/分）、一种握姿。
单数据集上的网格搜索极易过拟合 —— 我第一轮搜到
`crest_min_x100=110` 时误差 2%，但 80 就变 16%、140 变 32%，
**这种"动一点就崩"的解是不敢用的**。

所以我加了两道保险：
1. 只接受**参数邻域都稳**的解（`crest` 直接关掉，就没有这个敏感点了）
2. 用**合成信号在 60~120 步/分**做交叉检查，防止只在 74 步/分这一个点碰巧对

**还需要更多的真实数据**（不同步频、跑步、走走停停）。
请再录几段，然后用 `tools/step_search.py` 多文件联合评估：

```
python tools/step_search.py imu_logs/walk1.csv imu_logs/walk2.csv imu_logs/run.csv \
       --steps 50,62,300 --top 20
```

### 新增的调参工具（这套东西以后能反复用）

| 工具 | 作用 |
|---|---|
| `tools/step_tune.py` | 把 C 定点实现逐行照搬到 Python，拿录好的数据几秒跑一轮 |
| `tools/step_search.py` | 网格搜索 + 稳健性检查（邻域扰动）+ 防过拟合的合成交叉检查 |
| `tools/step_eval.py` | 评估候选参数，同时报"真实误差"和"跨步频合成误差" |

> ⚠️ 仿真器必须**逐行照搬**，不能用 numpy 重写成浮点版：
> 算法里全是 Q10/Q15/Q20 定点、四舍五入右移、整数开方、
> 以及"方差不能用 E[x²]-E[x]²"这类规避手法。
> 浮点重写会得出**不一样的结果**，调出来的参数搬到设备上就不准了。

## 一之四、🔴 WiFi 扫描"点了没反应"

### 根因

`hook_scan_start()` 里第一行是：

```c
if (!s_started) {
    return -1;          /* 服务没启动就直接失败 */
}
```

而 app 启动时**故意没有调用** `wifi_service_init()` ——
我当时的设计是"WiFi 协议栈吃 50KB RAM，等用户真要用再起"。

**但没有实现"按需启动"那一半**。结果：用户点"扫描附近网络"，
服务根本没起来，直接返回失败 —— 界面什么都不显示。

### 实测数字（顺便发现超时也设小了）

```
首次启动 WiFi 协议栈 : 8.1 秒（全量 RF 校准；之后走 NVS 缓存会快很多）
扫描本身             : 2.8 秒
```

界面原来的扫描超时是 **12 秒** —— 而"按需启动协议栈 + 扫描"最坏要 11 秒，
**就卡在边界上**，用户很容易看到"扫描超时"。

### 修法（两处）

1. **`hook_scan_start()` / `hook_connect()` 里按需启动协议栈**：
   谁先要用谁负责 `wifi_service_init()`。保留"不用 WiFi 就不占 RAM"，
   又不会"点了没反应"。
2. **扫描超时 12s → 25s**，宁可多等也不要误报。

另外把 app 启动流程也改了：**开机就初始化 WiFi**。
理由：没备份电池的情况下"连 WiFi 对时"是这个版本的核心功能，
实测 3.8 秒完成且 RF 校准会缓存，值得这 50KB。
（原来"按需启动"的顾虑其实成立，但体验代价更大。）

### 验证

```
开机后直接 wifi status  -> WiFi: 可用（不用手动 wifi on）
开机后直接 wifi scan    -> 2.8 秒扫到 12 个网络
```

## 一之五、🔴 用户实测反馈的三个界面 Bug

### Bug 1：小键盘点数字键打出字母

**现象**：切到数字层后，键上显示 "1"，按下去却输入 "q"。

**根因**：创建键时把 `s_layer[初始层][r][c]` 的**字符指针**存进了
`lv_obj_set_user_data()`，回调里直接用那个指针：

```c
/* 创建时 */
lv_obj_set_user_data(b, (void *)ch);      /* ch = s_layer[0][r][c] */
/* 回调里 */
const char *ch = lv_obj_get_user_data(btn);   /* 永远是初始层那个字符 */
```

而 `layer_refresh()` 切层时**只改了标签文字，没有更新这个指针**。
于是"显示"和"实际输入"从此脱钩。

**修法**：user_data 只存 **(行,列) 编号**，回调里用
`s_layer[kb->layer][r][c]` **现查**。层变了自然就查对了。

> 教训：把"会变的状态"在创建时快照下来，是这类 bug 的常见来源。
> 凡是"显示"和"行为"要一致的地方，都应该**从同一个来源现查**，
> 而不是各存一份。

### Bug 2：键盘上"退格""完成"显示成矩形（豆腐块）

**这已经是同一个坑第四次踩了**
（前三次：日期格式串的"年月"、设置页值列、分隔符"·"）。

原因还是那句：`make_btn()` 把字体写死成 `W_FONT_SMALL`
（Montserrat，**只有 ASCII**），而 "退格""完成"是中文。

**修法**：新增 `make_fn_btn()`，功能键一律用 `watch_font_cn(14)`；
切层键 / 空格 / 退格 / 完成 / 取消 全部改走它。

**顺带验证**：这几个中文**本来就在字库里**（`check_all_literals.py` 确认
"退格/完成/空格/取消/输入/密码"全部完整）—— 所以问题确实是
"字体没选对"，不是"缺字"。
（缺字和选错字体在屏幕上是**一模一样**的豆腐块，只能靠工具区分。）

> 这四次踩坑说明：**光靠"记得用中文字体"是防不住的**。
> 所以已经有了 `w_label_create_auto()`（按内容自动选字体）和
> `tools/check_fonts.py`（静态检查）。这次是手写 `make_btn` 绕过了这两道防线。

### Bug 3：操作过程中途息屏（最严重的一个）

**现象**：用户正在点屏幕，屏幕突然灭了。

**根因**：息屏计时器的"用户活动"来源**只有一个**，而且是错的：

```c
/* power.c 的轮询回调，50ms 一次 */
if (touch_pressed()) {          /* 读触摸中断脚 GPIO14 */
    s_last_active = now_us();
}
```

而 `power_notify_activity()` 这个正确的接口 —— **从来没有任何人调用过**
（grep 全工程只有定义，没有调用点）。

问题在于**轮询会漏事件**：
   - 电源轮询 50ms 一次，可是用户快速点击时，"按下"的窗口可能比这还短
   - 一旦漏掉几次，计时器就以为没人操作 → 15 秒到 → 中途息屏
   - 而 LVGL 其实**每 5ms** 就读一次触摸（`bsp.c` 的 `touch_read_cb`），
     信息一直是有的，只是没接到电源模块上

**修法**：把活动来源从"轮询"改成"**事件上报**"：

```
bsp.c: touch_read_cb()        ← LVGL 每 5ms 调，一次不漏
   检测到按下 -> w_screen_notify_activity()
                    |
                    v
power.c: hook_activity()
   - 屏幕灭着？ -> 只亮屏（吃掉这一次操作）
   - 屏幕亮着？ -> s_last_active = now
```

为此在 `w_screen_hooks_t` 里加了 `notify_activity` 钩子，
电源模块的轮询**只保留兜底**（手指一直按着不动时也算有活动），
不再承担主判断。

> 教训：**"轮询"和"事件"要分清**。需要精确不漏的地方必须用事件回调；
> 轮询只适合"状态类"的判断（比如"屏幕现在是亮是灭"）。
> 用轮询做"有没有发生过某事"，漏事件是必然的，只是概率问题。

## 一之六、🔴 WiFi 页"输完密码点完成，又跳回扫描列表"

> 用户实测反馈。这个 bug 让整个 WiFi 功能看起来像坏的，
> 但其实**连接已经在后台发起了**。

### 现象

选网络 → 输密码 → 点"完成" → **界面跳回扫描列表**，
看不出密码有没有被接受，也看不出在不在连接。

### 根因：这个页面**没有状态机**

`wifi_page_build()` 末尾是：

```c
/* 已连上时不用自动扫描 */
if (st.state != W_WIFI_CONNECTED) {
    start_scan();          /* ← 无条件重扫 */
}
```

而 `start_scan()` 会**清空列表 + 把状态文字改成"扫描中"**。

于是完整的事件链是：

```
点"完成"
  -> password_done() 里 h->connect() 发起连接（后台真的在连）
  -> w_modal_refresh() 重建页面
  -> 此时状态是 CONNECTING
  -> 但末尾那句 start_scan() 照样执行
  -> 清空列表、状态改成"扫描中"
  -> 用户看到：跳回扫描列表，仿佛什么都没发生
```

**连接其实成功了没有？不知道** —— 因为界面把用户甩回了起点，
而且 CONNECTING 分支里那句 `set_status(W_STR_WIFI_CONNECTING)`
**紧接着就被 `start_scan()` 覆盖掉了**。

### 修法：补一个正经的状态机

```c
switch (st.state) {
case CONNECTED:  显示 SSID/IP/对时 + 断开/重新对时;  return;   /* 绝不扫描 */
case CONNECTING: 显示"正在连接 <SSID>" + [取消连接];  return;   /* 绝不扫描 */
case FAILED:     显示"连接失败（密码错或信号太差）" + [重新扫描]; return;
default:         显示"未连接/正在重连" + [扫描按钮] + 列表;
}
```

四个关键点：

1. **CONNECTED / CONNECTING / FAILED 三条路都 `return`**，
   只有 IDLE 才会走到建列表和扫描那段代码 —— 从结构上杜绝"跳回扫描"
2. **加 `last_state`，状态一变就重建页面**：
   轮询里比较当前状态和上次记录的，不同就 `w_modal_refresh()`。
   这样连接成功了界面自动切到"已连接"视图，失败了自动显示失败原因。
3. **`ever_scanned` 标志**：只有**第一次进页面**才自动扫一次；
   之后重建页面时用已有结果重画列表，不再重扫（这正是 bug 的根源）
4. **CONNECTING 时显示 SSID 和"取消连接"按钮**，用户知道在连谁、能中止

### 验证

用错密码发起连接，串口轮询状态：

```
[ 1.2s] WiFi: 可用  状态=连接中
[ 3.5s] WiFi: 可用  状态=失败      <- 2.3 秒后正确落到 FAILED
```

状态机走得通，界面会从"连接中…"切到"连接失败（密码错或信号太差）"，
不再把用户甩回扫描列表。

## 一之七、🔴 连接失败后"扫描不出 wifi"

> 修完上一节的状态机之后，用户又实测报了这个。
> 是**上一节修复引入/暴露的另一个问题**，根因不同。

### 现象

连接失败后（界面显示"连接失败"），点"重新扫描"扫不出任何网络。

### 根因：`return` 跳过了公共资源的创建

我修状态机时把 FAILED 分支写成了：

```c
switch (st.state) {
case W_WIFI_CONNECTED:  ...  return;
case W_WIFI_CONNECTING: ...  return;
case W_WIFI_FAILED:
    set_status(W_STR_WIFI_FAILED, ...);
    wide_btn(..., rescan_cb);
    return;               /* ← 这里 */
...
}

/* 列表容器 —— 建在 switch 之后 */
ui.list = lv_obj_create(parent);
```

于是 **FAILED 状态下 `ui.list` 是 NULL**，而 `show_scan_list()` 开头就是：

```c
if (!h || !ui.list) {
    return;               /* 扫到了也没地方放 */
}
```

**扫描其实成功了**（串口验证过确实能扫到 12 个网络），
只是没有容器可以承载结果，屏幕上什么都不显示。

### 修法

1. **把列表容器的创建提到 `switch` 之前** —— 只要后面有分支会
   `return`，公共资源就必须在 `return` 之前建好
2. **FAILED 分支改成 `break`**，让它继续走到"填充列表"那段
   （附注释说明为什么不能 return，免得以后又改回去）

### 验证

```
1) 用错密码连接 -> 进入 FAILED 状态          ✓
2) 在 FAILED 状态下扫描 -> 12 个网络 / 2.8 秒  ✓
```

### 教训

这是**同一个函数里两个 `return` 引发的两种不同故障**：
- 第一个（原来的 `start_scan()` 无条件执行）导致"跳回扫描列表"
- 第二个（FAILED 里的 `return`）导致"扫不出 wifi"

根子上都是**"靠执行流顺序来保证某段代码会运行"**这种脆弱写法。
更稳的写法是：公共资源（容器、定时器、状态）在**进入分支之前**
统一准备好，分支里只做"往容器里放什么"。

## 一之八、🔴 RTC 写不进去 —— 差整整 30 年

> **这是整个 v0.4.0 里最严重的一个 bug**：它让"WiFi 对时"这条
> 核心链路**完全失效**，而且伪装得极好。

### 现象

SNTP 明明对时成功了，RTC 却拒绝写入：

```
I (10671) WIFI: SNTP 对时成功：UTC 1791363106（本地按 settings 时区换算）
E (10672) RTC: rtc_pcf_set_time(189): 时间字段非法: 1996-10-07 08:51:46
E (10673) DATA_HUB: data_hub_set_epoch(311): 写 RTC 失败
E (10673) APP: 写 RTC 失败: ESP_ERR_INVALID_ARG
```

epoch `1791363106` 是 **2026-10-07**，但算出来是 **1996-10-07** —— **正好差 30 年**。

### 定位过程（写了个宿主机程序，不靠猜）

把 `civil_from_days()` / `days_from_civil()` 抠出来编成 PC 程序，
逐一对比标准 Unix 时间换算。中间量立刻暴露问题：

```
对照组 epoch=946684800（应为 2000-01-01）：days=0 -> 1970-01-01   ← 差 30 年
z=729244 era=4 doe=144856 yoe=396 yy=1996                        ← era 应为 5，yy 应为 2026
```

### 根因：两个"天数"基准不一致

```c
/* 标准算法，719468 是**1970-01-01** 的基准偏移 */
static void civil_from_days(int32_t days, ...)   /* 参数语义：自 1970 起的天数 */

/* 但调用方喂进去的是"自 2000 起的天数" */
int32_t days = (epoch_sec - RTC_EPOCH_2000) / 86400UL;   /* 自 2000 起！ */
```

`RTC_EPOCH_2000` 是**相对 1970 的秒数**（946684800），
但除以 86400 得到的是**相对 2000 的天数**。两者差 **10957 天**。

### 为什么之前所有测试都没发现（关键）

因为 `rtc_pcf_get_epoch()` 回读时**也偏了同样的 30 年**，
**两个错误互相抵消**：

```
写入 epoch X  →  算出 1996 年（错）→ 存进 RTC（错）
从 RTC 读回    →  算出 epoch X（对！）
```

所以"写进去再读出来"的往返测试**永远是绿的**。
只有拿**真实 epoch**去写、或从别的途径核对日期，才会暴露。

> 之前 `time set 2026-10-06 12:00:00` 的测试之所以"通过"，
> 是因为它走的是 `rtc_pcf_time_t` → `rtc_pcf_set_epoch` 这条路，
> 而读回来又是同一条路的逆运算 —— 自洽，但都是错的。

### 修法

加一个常量，**set 加、get 减，必须成对**：

```c
#define DAYS_1970_TO_2000  10957     /* 2000-01-01 相对 1970-01-01 的天数 */

/* set：自 2000 的天数 -> 自 1970 的天数 */
int32_t days = (int32_t)((epoch_sec - RTC_EPOCH_2000) / 86400UL) + DAYS_1970_TO_2000;

/* get：自 1970 的天数 -> 自 2000 的天数 */
const int32_t days = days_from_civil(t.year, t.month, t.day) - DAYS_1970_TO_2000;
```

### 验证（宿主机程序，7 组用例全过）

```
epoch        | 算出              | 期望
946684800    | 2000-01-01 00:00:00 | 2000-01-01 00:00:00 | OK
1791363106   | 2026-10-07 08:51:46 | 2026-10-07 08:51:46 | OK
1700000000   | 2023-11-14 22:13:20 | 2023-11-14 22:13:20 | OK
2147483647   | 2038-01-19 03:14:07 | 2038-01-19 03:14:07 | OK
4294967295   | 2106-02-07 06:28:15 | 2106-02-07 06:28:15 | OK
（外加往返一致性检查，全部 OK）
```

> ⚠️ **教训：往返测试（write→read→比对）证明不了正确性。**
> 如果正反两个方向有**对称的错误**，往返测试永远是绿的。
> 必须拿**外部权威值**（这里是标准 Unix 时间换算）做单点核对。

## 一之九、🔴 WiFi 卡在 "connecting" 引发的连锁故障

> 用户报的三个症状，排查后发现是**同一个根因**。

### 三个症状，一个根因

| 用户报的症状 | 真实原因 |
|---|---|
| "WiFi 扫描不出来" | 扫描被驱动**拒绝** |
| "输对密码也连不上" | `set_config` 被拒，**新密码根本没写进去** |
| "点重新对时没反应" | 连不上→拿不到 IP→**SNTP 压根不启动** |

驱动卡在 connecting 状态时会拒绝一切操作：

```
E wifi:sta_scan: STA is connecting, scan are not allowed!
E wifi:sta is connecting, cannot set config
```

而我的代码里 **`esp_wifi_connect()` 之后没有任何超时兜底** —— 一旦卡住就永久卡死。

### 修法（四处）

1. **连接超时 15 秒**：`hook_get_status()` 里顺手判定，超时则强制复位。
   断开动作放在**锁外**执行（`wifi_force_idle()` 内部也要拿锁，持锁调用会自死锁）。
2. **扫描前自救**：`hook_scan_start()` 发现驱动还在连接，先 `wifi_force_idle()` 再扫。
   实测日志：`W WIFI: 驱动还在连接中，先断开再扫描`
3. **`set_config` 前先断开并等断开事件**：不等的话驱动会拒绝配置
   （`E wifi:sta is connecting, cannot set config`），新密码静默丢失。
4. **`wifi reset` 命令**：`esp_wifi_stop()` + `deinit()` + 重新 `init()`，
   并清除保存的凭据。用于"连失败几次后一直连不上"——
   驱动内部认证状态会变脏，只有彻底重建才能回到干净状态
   （实测断电重启也能恢复，但不该让用户去拔电）。

### 另外修的两处 STA 配置

- **`threshold.authmode` 改成 `WIFI_AUTH_OPEN`（不筛）**：
  它的含义是"只连加密强度不低于此值的 AP"，设成 `WPA2_PSK`
  遇到 WPA3 / 过渡模式会被驱动过滤（reason=211）。
  实测手机热点就是 `authmode=7`（WPA2/WPA3 过渡）。
- **补上 PMF 和 SAE PWE 配置**：
  `pmf_cfg.capable=true / required=false`（WPA3 强制 PMF，过渡模式通常支持但不强制）；
  `sae_pwe_h2e = WPA3_SAE_PWE_BOTH`（单设一种的话，对端只支持另一种时握手会失败）。

### 新增两个诊断日志（这次排查全靠它们）

1. **扫描时打印每个 AP 的加密方式和信道**：
   `AP 'CWQLYK' authmode=7(WPA2/WPA3) ch=6 rssi=-48`
   没有这行，根本看不出"是不是加密方式不匹配"。
2. **连接时打印密码的字节码**（不打明文）：
   `密码字节码: 34 32 35 31 36 39 31 31`
   长度不对时，光看文本看不出"末尾多了个不可见字符"。
   **这个日志直接帮我发现了"密码 9 位"其实是我自己测试脚本写错了。**

## 一之十、🔴 "重新对时"点了没反应（我自己引入的 bug）

### 根因：幂等检查写在了置位之后

为了让"重新对时"有界面反馈，我加了 `syncing` 状态。但检查写错了顺序：

```c
sntp_mark_syncing();                    /* 把 syncing 置为 true */
if (esp_sntp_enabled()) {
    const bool already = s_st.syncing;  /* 永远是 true！ */
    if (already) return;                /* 永远 return，什么也不做 */
}
```

`mark_syncing()` 已经把 `syncing` 置成 true，紧接着再读它当然是 true ——
于是**所有"服务已启动"情况下的手动对时都被直接吞掉**。

### 附带问题：`esp_sntp_restart()` 不可靠

实测"开机首次对时成功，手动重新对时 15 秒超时"。
`esp_sntp_restart()` 只重置 lwIP 的 SNTP 状态机，**不重新解析服务器名**。

### 修法

1. 幂等检查**前置**到 `sntp_mark_syncing()` 之前（附注释警告保持这个顺序）
2. 用 `esp_sntp_stop()` + 重新 `init()` 替代 `restart()`，
   走和"首次成功"完全相同的代码路径
3. 界面加**对时三态**显示：`对时中… / 已对时 / 对时失败`
   （原来只有两态，点了之后文字照样显示"已对时"，用户以为按钮坏了）

## 一之十二、🔴 表盘时间慢 8 小时 —— SNTP 的 UTC 被当成墙上时间

> 用户实测："连上 WiFi 自动校准时间成功了，时间校准正确，但是时区不对，
> 当前时区是北京时间，时间页面没有 +8 小时"

### 根因：时区换算这一步**根本不存在**

项目里对"RTC 存什么"的约定是**矛盾**的，两处注释说法相反：

| 位置 | 说法 |
|---|---|
| `data_hub.c` 顶部 | "RTC 芯片里存的就是**墙上时间**（本地时间）" |
| `app.c` 对时注释 | "SNTP 给的就是 UTC，和 RTC 存储口径一致，直接写。本地时间由时区换算（**显示时才算**）" |

**实际生效的是 `data_hub.c` 那套** —— 因为：

- `sample_time()` 从 `rtc_pcf_get_time()` 直读，**不做任何时区换算**
- 表盘 `watch_page_home.c` 直接显示 `t->hour / t->minute`
- **`SETTINGS_TIMEZONE` 全工程没有任何地方真正使用它**
  （`time_hook_get_tz` / `get_tz_quarters` 钩子定义了，但**没有调用方**）

所以实际链路是：`SNTP 的 UTC` → 原样写 RTC → 表盘直接显示 UTC。
北京时间（UTC+8）自然就**慢 8 小时**。

### 修法

在唯一缺失的那一环补上换算 —— 写 RTC 之前加时区偏移：

```c
const int tz15 = settings_get_or_default(SETTINGS_TIMEZONE);  /* 北京 = 32 */
const int32_t offset_sec = (int32_t)tz15 * 15 * 60;
const uint32_t local_epoch = (uint32_t)((int64_t)utc_epoch + offset_sec);
data_hub_set_epoch(local_epoch);      /* 存进去的是墙上时间 */
```

时区默认值本来就是 32（+8 区），所以**默认就是北京时间**，符合用户要求。

### 验证（换算核对）

```
SNTP UTC      : 2026-10-07 08:51:46 UTC
时区设置      : 32 (15分单位) = UTC+8
写入 RTC      : 2026-10-07 16:51:46   <- 墙上时间
修复前表盘显示: 08:51（慢 8 小时）
修复后表盘显示: 16:51（正确）
```

> 顺带修了 `app.c` 里那段**错误注释**。注释和实现说法相反是很危险的 ——
> 这次就是照着错误注释写的代码。写注释时要和实际生效的那套对齐。

## 一之十三、🔴 已保存的网络还要重新输密码（而且重输也连不上）

> 用户实测："我主动断开 WiFi 后重新点那个 WiFi，并没有直接连接，
> 而是重新输入密码。而且我重新输入正确的密码后连接失败，
> 提示我密码错误或者信号差。"

这里有**两个独立的 bug** 叠在一起。

### Bug A：界面从不检查"这个网络是否已保存"

```c
/* watch_page_wifi.c 的 ap_clicked */
if (secure) {
    ask_password(ssid);        /* 只要加密就问密码 —— 从不看是否已保存 */
} else {
    h->connect(ssid, "");      /* 开放网络直接连 */
}
```

**修法**：页面构建时读一次已保存的 SSID，点击时比对：

- 加密 + 就是已保存的那个 → `h->connect(ssid, NULL)` 直接连
- 加密 + 别的网络 → 问密码
- 开放网络 → 直接连

### Bug B（更严重）：传空密码会把已保存的密码**覆盖掉**

`hook_connect()` 里：

```c
wifi_config_t cfg;
memset(&cfg, 0, sizeof(cfg));                    /* 先全部清零 */
strncpy(cfg.sta.ssid, ssid, ...);
if (password && password[0]) {                   /* ← 密码为空就什么都不写 */
    strncpy(cfg.sta.password, password, ...);
}
...
creds_save(ssid, password ? password : "");      /* ← 还把空串存进 NVS！ */
```

密码为空时：配置里 `password` 字段是**空的**（刚 memset 过），
`esp_wifi_set_config()` 把空密码写进驱动；更糟的是
`creds_save()` 把 NVS 里原本**好好的密码也覆盖成空串**。

所以一旦走了一次"没带密码的连接"，保存的密码就被毁了 ——
这正是"重输正确密码后依然失败"的原因。

**修法**：引入 `eff_pass`（最终真正生效的密码）：

```c
char eff_pass[WIFI_PASS_MAX] = { 0 };
if (password && password[0]) {
    strncpy(eff_pass, password, ...);            /* 有传入就用传入的 */
} else {
    /* 没传入：回填 NVS 里保存的密码（且 SSID 必须匹配，别把 A 的密码用到 B 上）*/
    creds_load(saved_ssid, ..., saved_pass, ...);
    if (strcmp(saved_ssid, ssid) == 0) strncpy(eff_pass, saved_pass, ...);
}
```

并把**所有下游**（写进 cfg、日志、`creds_save`）统一改成用 `eff_pass`。
一共 4 处：长度日志、字节码日志、cfg 赋值、`creds_save`。

> 教训：函数里一旦引入"最终生效值"，就要**把所有下游都改过去**。
> 只改一半比不改更危险 —— 这次就是漏了 `creds_save`，
> 表现成"密码越连越坏"。

## 二、🔴 顺带挖出的两个严重 Bug（比新功能更重要）

### Bug 1：加速度换算公式错误，**所有加速度都偏大一倍**

`components/imu/include/qmi8658c.h`：

```c
int32_t lsb = 32768 >> (int32_t)fs;     // 错：±2g 算出 32768
```

正确是 `16384 >> fs`：

| 量程 | 错误值 | 正确值 |
|---|---|---|
| ±2g | 32768 | 16384 |
| ±4g | 16384 | 8192 |
| ±8g | 8192 | 4096 |
| ±16g | 4096 | 2048 |

**影响**：加速度整体偏大一倍。而计步门限（60mg）、带通滤波器系数、
`peak_thresh_mg` 全是按 mg 定的 —— 表现成"参数怎么调都不对"。
**在修好这个之前，所有调参工作都是白做的。**

**为什么难查**：不崩、不报错、波形还挺平滑，只是整体缩放。
我排查时依次排除了：
量程没写对（读回 CTRL2=0x27，确实是 ±8g）→
厂商系数不同（SensorLib 也是 `8.0/32768`，和我一致）→
摆放姿态 → LPF 过渡 → 自检代码自己写错了。

**最后怎么抓到的**：把换算函数抠出来写成宿主机小程序单独跑
（`gcc -O0 t.c && ./t.exe`），把四个量程的返回值打出来，
一眼看出 `32768>>0` 还是 32768。**比烧板子快得多。**

**修的过程还踩了一个元坑**：我第一次"修复"写成 `1 << (15 - fs)`，
以为改了 —— 其实和 `32768 >> fs` **完全等价**（`32768>>0` 还是 32768），
一点没修。第二次才改对。

**教训**：
- 换算系数要用**代入已知值验证**的方式检查，光看代码觉得很合理
  （32768 是 2^15，`>>fs` 看着很顺）
- 现在 `imu_raw` 命令会把四个量程的 LSB/g 打出来，必须显示
  `16384 / 8192 / 4096 / 2048`；板子平放静止 |a| 必须约 1000 mg

### Bug 2：自动续录会让数据错乱（静默错误数据）

插 USB 会复位芯片（`rst:0x15 USB_UART_CHIP_RESET`），
复位后自动续录，从**缓冲边界（第 331 帧）**开始数据错乱：

```
#330  b7390000fffff0ffc7050000   t=14775  ax=-1   ay=-16  az=1477   正常
#331  fcfffcfffcff0000db050000   t=0      ax=-4   ay=-4   az=-4     **乱**
```

**最坑的是：校验和照样通过** —— 数据确实写进去了，只是内容是坏的。
所以只看"校验失败行数 = 0"完全发现不了。

**两个修法**：

1. **改成每帧落盘**（原来是攒够 341 帧 = 6.8 秒再写）。
   重估代价后发现"攒批"根本不值得：
   - 数据率只有 600 B/s，一帧一写也就 50 次/秒
   - Flash 擦写寿命 10 万次 → 要写坏一个扇区需**连续录几百小时**
   - 而攒批的代价是"掉电丢 6.8 秒 + 续录边界错乱"

2. **加跨复位时间偏移**：时间戳来自 `esp_timer_get_time()`，
   **每次开机从 0 重算**，所以"录 6 秒 → 复位 → 续录"会出现
   时间戳倒退（实测相邻两帧差 **-16805 ms**），后处理整段废掉。
   续录时把 `time_offset` 设成 `last_ms - now + 1`，保证整个文件单调递增。

**验证**：修复后 887 帧 / **49.8 Hz** / 帧间隔 20ms
（只有复位处一个 92ms 缺口，符合预期）/ 时间戳单调递增 ✓

## 三、新增功能

### 1. IMU 数据录制（解决"USB 线太短"）

| 环节 | 实现 |
|---|---|
| 存哪 | SPIFFS 分区（`partitions.csv` 的 `storage`，11MB，之前一直空着） |
| 存什么 | 原始加速度 12 字节/帧：`uint32 t_ms` + `int16 ax/ay/az` + `uint16 保留` |
| 采样 | 50Hz（从 motion 采样任务里顺手喂，不再额外读 I2C） |
| 容量 | **约 5 小时**（600 B/s ≈ 2.16 MB/小时） |
| 写满 | 环形覆盖最旧的（用户选择） |
| 读回来 | 串口 `rec get` → PC 端 `tools/imu_dump.py` 存 CSV |

**为什么只录原始加速度**：原始数据可以**反复用不同参数重算**，
不用重新走路。录中间量就只能看当时的算法状态，改个参数就得重走。

**导出格式带校验**（`<帧序号> <12字节hex> <校验和>`）：
实测这块板的 USB-Serial-JTAG 在持续高速输出时会丢字节，
而且丢得隐蔽 —— 行数是对的（换行没丢），但行**内部**字段错位。
第一版用纯 CSV 输出，导出结果后半段是垃圾且**没有校验根本发现不了**。
现在每行带异或校验和 + 帧序号，`imu_dump.py` 逐行验，还能定位缺了哪几帧。

### 2. WiFi 连接 + SNTP 校时

- **扫描列表选 SSID**（点一下选中，不用手敲）
- **小键盘输密码**（4 层循环：小写/大写/数字/符号，**明文显示**便于自检）
- 密码**存 NVS**，开机自动重连
- 连上后**自动 SNTP 对时** → 写 RTC（存 **UTC**）
- 连上后**保持连接**（用户要求），提供**手动断开**
- 连上后弹提示："WiFi 保持连接会比较费电，不用请断开"

### 3. 息屏（只关背光）

- 无触摸 N 秒（settings 里可配）→ `bsp_backlight_set(0)`
- **息屏后第一下触摸只亮屏**，不触发界面动作（用户要求）
- 录制 IMU 期间**禁止息屏**（用引用计数，见下）
- **不做低功耗**：CPU / LVGL / IMU 全部照跑（用户要求先不做）

### 4. 开发人员选项子页面

```
设置页
├── 亮度 / 自动息屏 / 抬腕亮屏 / 步数目标 / 身高 / 体重 / 时钟状态
├── WiFi 连接            ← 放设置页（普通用户也要用）
└── 开发人员选项
    ├── IMU 录制          [开始录制] [停止录制] + 状态 + [删除全部]
    ├── 时间校准          年月日时分秒 各带 [−] [+]，填 **UTC**
    └── 系统信息          固件 / 内存 / PSRAM / 运行时长 / 存储占用
```

### 5. 手动时间校准（填 UTC）

- 年月日时分秒各一行，带 `[−]` / `[+]` 按钮
- **填的是 UTC**（用户明确要求，方便以后切时区）
- 日期回绕做了闰年判断（2 月在闰年是 29 天）
- 写 RTC 时**不做任何时区换算**；表盘显示时才按 settings 时区换算

### 坑 19 详述（最隐蔽的一个）

```c
/* 第一版：逐个文件名 fopen 探测 */
for (int i = 1; i <= 9999; i++) {
    if (file_exists(name)) { ... }
}
```

9999 次 `fopen` 是 9999 次 Flash 读；更致命的是
**Flash 操作期间不喂任务看门狗**（IDLE0 得不到调度），
实测 4.5 秒内一次都没喂 → `task_wdt` 每 5 秒报一次，
`app_main()` 永远回不来，**串口命令行根本没起来**。

改成 `opendir` / `readdir` 真正遍历目录，代价降到目录项数量级。

> **最严重的一个 bug**：**RTC 写入差整整 30 年**，导致 WiFi 对时
