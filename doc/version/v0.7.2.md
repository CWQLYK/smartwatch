## 一、一句话总结

**本版把"电池供电"这条路上的三颗雷全部拆掉，并留下两只"黑匣子"。**

1. **松开 PWR 键就断电** → 原理图上的电源自锁脚 `SYS_EN`(GPIO41) **代码里从来没登记过**，
   固件从不拉高它。新增 `board_power_hold()`，启动第一步就把电源锁上。
2. **每 7.5 秒自动重启一次** → 没有 USB 主机时，IDF 的控制台读**立即返回错误**
   （`usb_serial_jtag_vfs.c` 里的 `TODO IDF-14303`），命令行任务于是**空转**，
   把空闲任务饿死 → 任务看门狗 5 秒后 panic（+约 2.5 秒启动 = 7.5 秒一轮）。
   加"无主机守卫"：没主机就挂起命令行任务，插上 USB 再唤醒。
3. **偶发整机僵死**（屏幕冻住、串口也没反应、却不重启）→ **是我修第 2 条时引入的死锁**：
   守卫可能正好把命令行任务挂在**打印中途**，于是它**攥着 stdout 流锁不放**，
   所有打日志的任务永久阻塞。修法：挂起前先用**非阻塞** `ftrylockfile(stdout)` 拿住流锁。

**为什么这三条这么难查**：它们的共同特征是**事后取证手段全部失效** ——
不复位（没有复位原因）、无 panic（没有 coredump）、连串口都没反应。
所以本版顺手做了两件工具：**复位黑盒**（每次启动记录复位原因 + 电池电压）与
**卡死哨兵**（独立跑在 CPU 1 上，界面一停就把全部任务现场写进 Flash）。
第 2、3 条就是靠它们查出来的。

## 三、根因与关键决策（都带源码级证据）

### 3.1 ★★ 电源自锁：`PWR` 键只负责"给一下电"，**让电一直供下去的是固件**

**现象**：插 USB 一切正常；**一用电池，必须一直按住 PWR 键才运行，松手就黑屏断电。**

诊断只采信两处证据（**否掉了两个"看起来很像"的错误来源**）：
- ✅ **本板 V2.1 原理图「KEYS」区逐线核对**（渲染成图看的）+ 官方硬件参考（`SYS_OUT=GPIO40`、`SYS_EN=GPIO41`）
- ❌ 否掉：`Watch-Player_IDF` 参考工程 —— 它服务的**不是这块板**（按键 6/7/8、SD 检测 15、外设电源 5，而本板 GPIO4~8 是 LCD、15 是背光）
- ❌ 否掉：GFX 库里的 `pinMode(16 /* BAT_PWR */)` —— 那属于 **AMOLED 2.41** 那块板

电路（已核对）：

```
B+ ──[R21 10K]──┬── Q5(AO3401 P-MOS) 栅极   ← R21 默认把栅极拉到 B+ ⇒ Q5 默认关断
                ├── D3 ── Key2(PWR 键) ── GND
                └── T2(SS8050) 集电极
SYS_EN ──[R22 1K]── T2 基极 ;  T2 发射极 ── GND
B+ ── Q5 源极 ;  Q5 漏极 ── VBAT（系统电源轨）
```

按 PWR → 经 D3 把 Q5 栅极拉低 → Q5 导通 → 电池上电；**松手后必须由 `SYS_EN` 拉高**（T2 导通 → 栅极拉低 → Q5 保持导通）才能自锁。
固件从没驱动过它 ⇒ 松手即断电。**插 USB 时 VBUS 直接供电，与 Q5 无关 → 这个缺陷在只用 USB 开发时永远看不出来。**

**两个实现细节（踩过才写的）**：
1. **必须先 `gpio_set_level(1)` 再 `gpio_config(OUTPUT)`**：反了的话，使能输出那一瞬间引脚驱动低电平 → 电池供电当场被切断。
   可行性已核 IDF v5.5.4 源码：`gpio_config()` 只切输入/输出使能与上下拉、**不写输出数据寄存器**；`gpio_set_level()` 对还没配成输出的脚也安全。
2. **不能放在 `board_init()` 的幂等判断之后**，也不能因 I2C 失败被跳过 —— 电池供电时它是"保命"的那一步。

**⚠️ 固有局限**：电池供电时**复位/panic 会掉电**（复位期间引脚回高阻 → Q5 关断），需要再按一次 PWR。硬件特性，软件绕不过去。

### 3.2 ★★ 每 7.5 秒重启：没有 USB 主机时，**控制台任务空转**

**排查链条**（由复位黑盒 → coredump → 逐任务栈 → IDF 源码）：

| 步 | 证据 |
|---|---|
| 1 | 复位黑盒：**不是掉电**（0 次），是 `TASK_WDT` ×6；电池 3750mV/40% 正常 → 排除供电 |
| 2 | `idf.py coredump-info`：`IDLE0 (CPU 0) did not reset the watchdog in time`；`IDLE0` 自己在空闲循环里 → **是别的任务占了 CPU 0** |
| 3 | "crashed task" = **`console_repl`**，栈顶停在 `vPortExitCritical` → 典型"反复调用立即返回的读、在系统调用里空转" |
| 4 | IDF 源码实锤 ↓ |

```c
/* components/esp_driver_usb_serial_jtag/src/usb_serial_jtag_vfs.c */
static ssize_t usb_serial_jtag_read(int fd, void* data, size_t size)
{
    if (!usb_serial_jtag_is_connected()) {
        // TODO: IDF-14303
        return -1;        /* ★ 没有 USB 主机时【立即返回】，不阻塞 */
    }
```

**因果链**：没有主机 → 读立即返回 -1 → `linenoise` 不带延时地重试 → **死循环**（IDF 已知问题，工程改不了 IDF）
→ `console_repl`（**优先级 2、绑核 CPU 0**）→ **饿死 `IDLE0`（优先级 0、同一个核）**
→ 5 秒看门狗 panic → 重启约 2.5 秒 → **正好 7.5 秒一轮**（与实测完全吻合）。
`taskLVGL` 优先级 4 高于 2 ⇒ **界面照常刷新、看起来"只是闪一下"**（也与实测吻合）。

**修法**：1 秒周期的"无主机守卫"（跑在 esp_timer 任务里，优先级 22，不会被饿死）——
没主机就挂起 REPL 任务，主机回来唤醒。
**没有**采用"把空闲任务从看门狗里摘掉"那种掩盖法：那样 CPU 仍被转满，对电池供电是灾难（还正好抵消 v0.7.1 的省电）。

### 3.3 ★★ 静默硬死：**是本版守卫自己引入的死锁**（教训最重的一条）

**现象**：电池供电偶尔**整机僵死** —— 屏幕冻住、**串口也没反应**，而且**不复位、无 coredump**。

**取证为什么难**：事后手段全部失效。连"不发复位信号直连串口"（**先做了阳性对照**，证明该方法在健康机器上能读到输出）也读到 **0 字节**。

**卡死哨兵抓到的现场**：

```
开机 8 秒时：界面任务心跳连续 5 秒没有推进（心跳值 141）
任务         状态 优先 运行计数us   栈余量
IDLE0          就绪 0    6271652    696    ← 双核空闲累计 14s/16s ⇒ CPU 根本没在转
IDLE1          就绪 0    7731699    688
taskLVGL       阻塞 5    1194393    2656   ← 界面任务阻塞 ⇒ 界面已死
console_repl   挂起 22   122905     4928   ← ★ 优先级显示 22，而它创建时是 2
esp_timer      阻塞 22   15694      2164   ← ★ 优先级 22 的任务在阻塞
```

**决定性线索是"优先级继承"**：`console_repl` 的当前优先级是 **22** 而基准是 **2**
→ 说明**有优先级 22 的任务（`esp_timer`）在等它持有的锁**，优先级被临时继承上去了。
而它**被守卫挂起了、永远不会释放** → `esp_timer` 永久阻塞 → 依赖它、以及**所有要打日志的任务**接连阻塞 → 界面冻死。

那把锁是 **newlib 的 stdout 流锁**：`vTaskSuspend` 是"随时生效"的，
如果正好把它停在**打印提示符**中间，它就攥着 stdout 流锁睡着了；
而任何打日志的任务都要先拿这把锁 —— **第一个撞上的正是 `esp_timer`(22)**。
**只有电池供电才触发**，因为只有"没有 USB 主机"时守卫才挂起它。

**修法**：

```c
if (ftrylockfile(stdout) == 0) {   /* 非阻塞：拿住锁 ⇒ REPL 不可能正停在打印里 */
    vTaskSuspend(h);
    funlockfile(stdout);
}
/* 拿不到说明它正在打印 → 这一拍先不挂，下一秒再来（空转最多多 1 秒，远小于 5 秒看门狗） */
```

**教训（写给以后的自己）**：
1. **永远不要挂起一个可能持有锁的任务** —— "它会空转"和"它会被挂起在持锁状态下"是同一件事的两面。
2. **优先级被继承（`currentPriority > basePriority`）是"有人卡在锁上"的强信号**，这一条把范围直接缩到了 `esp_timer` ↔ `console_repl`。
3. **单方证据不足时先做阳性对照**（"直连读不到数据"要先证明这个方法在健康机器上能读到）。
4. **怀疑 panic 时先读 coredump 再烧录** —— 本次因为中途又烧了一次，Flash 里的 coredump 因 `app SHA256` 不匹配而无法解析。
5. **"不复位 + 无 coredump + 串口无响应"这类问题，必须在活着的时候把现场写进 Flash** —— 这就是哨兵存在的理由。

### 3.4 卡死哨兵的设计（每一条都是被现场逼出来的）

| 设计 | 为什么 |
|---|---|
| **独立任务、绑 CPU 1** | 实测僵死时控制台（固定 CPU 0）也死 → 至少 CPU 0 被占住，哨兵必须在另一个核上 |
| **不依赖 esp_timer** | 僵死时那条路可能一起死（本次就是：`esp_timer` 被锁死） |
| **判活只读 volatile 心跳**（`g_bsp_lvgl_beat`） | 若哨兵自己调 `uxTaskGetSystemState()`（要拿内核锁），而僵死方正好占着内核锁，哨兵会跟着卡住 → 现场永远写不出来 |
| **先写"最小标记"（不碰锁），再补任务表** | 补表有风险，但那时标记已经落盘 ✔ |
| **补表时 dump 栈顶 16 个字** | 只存栈指针（DRAM 地址）`addr2line` 翻译不出函数名；PC 压在栈顶那一段里，全 dump 出来离线筛代码段地址即可 |

## 五、明确**没做**的事（范围控制）

| 项 | 原因 |
|---|---|
| **卡死自动复位兜底** | 哨兵已能**记录**现场，但**不自动复位**：① 查病因阶段自动复位会掩盖现场；② 电池供电时复位会掉电（§3.1 的固有局限），复位了也起不来，等于关机。等病因都清掉再考虑。 |
| **长按 PWR 关机** | 自锁生效后，"关机"必须由固件主动拉低 `SYS_EN`。目前只能拔电池或等它耗尽。要做需要：读 `SYS_OUT`(GPIO40) + 长按计时 + 关屏提示，属**新功能**（下一版）。 |
| **电池低电段的硬件局限** | 电池 → `Q5` → `VBAT` → `Q4` → **ME6217 LDO** → 3V3。这是 **LDO 不是 buck-boost**：输入需 ≥ 约 3.5V 才能稳住 3.3V ⇒ **电池最后一段（约 3.6V 以下）实际用不了**，电量显示"还有 40%"时已进入危险区。**软件改不了**，只能换更大/更低内阻的电芯或改板（buck-boost）。 |
| **第二档省电**（收益最大） | 实测息屏仍有 **51mA** 底噪，大头是"CPU 240MHz 双核常开 + 面板"。需 CPU 降频 / `CONFIG_PM_ENABLE` + DFS + light sleep（tickless idle、给 SPI/I2C 加 PM 锁、配唤醒源）。风险最高，**建议单独立项**。 |
| 面板 SLPIN（1.5 档）、上滑入口修复、`hint_ok_cb` UAF、天气 epoch、布局更正 | 见 v0.7.1 文档 §五 与 `doc/智能手表-v0.7.1实施文档.md`（已逐行核实，待排期） |

## 八、本版本改动简单说明

**这一版不加任何新功能，只干一件事：让"拔掉 USB、只用电池"第一次真正能用。**

以前这块表只在插着电脑 USB 的情况下开发过，所以一接电池，问题连着来 —— 这一版把它们都拆了：

**① 松开 PWR 键就断电 → 已修**
原理图上有个"电源自锁"引脚（`SYS_EN`），**按 PWR 只是给一下电，真正让电持续供下去的是固件把它拉高**。
而代码里以前**根本没登记这个引脚**，所以只能一直用手指按着。现在开机第一步就把电源锁上，
**按一下 PWR 就能松手，手表继续运行**。（`power status` 里能直接看到锁存状态。）

**② 每 7.5 秒自动重启一次 → 已修**
原因很隐蔽：**不插 USB 时，命令行功能的读操作会立刻返回错误**，于是它变成"空转死循环"，
把系统里的空闲任务饿死，5 秒后看门狗就把整机重启（加 2.5 秒启动 = 7.5 秒一轮）。
界面之所以看起来"只是闪一下"，是因为界面任务的优先级比它高、还在正常跑。
现在加了"无主机守卫"：没插 USB 就把命令行任务挂起，插上再唤醒。

**③ 偶尔整机僵死（屏幕冻住、连串口都没反应）→ 已修**
**这条是我修上一条时自己弄出来的**：挂起命令行任务时，可能正好把它停在"打印"中途，
于是它攥着输出锁不放，所有要打日志的任务就永久卡住了。
修法是挂起前先拿住那把锁（拿不到就下一拍）。另外两条也留了教训：
"挂起一个可能持有锁的任务"是危险动作；"优先级被异常继承"往往就是死锁的指纹。

**④ 顺便留下两件长期好用的"黑匣子"**
这几条问题最难的地方是**事后什么痕迹都没有**（不重启、不崩溃、串口也没反应），所以：
- **复位黑盒**：每次开机记一条"为什么重启 + 当时电池电压"，`power log boot` 读；
- **卡死哨兵**：独立跑在另一个 CPU 核上，界面一停就把**所有任务的状态和现场**写进 Flash，`power log hang` 读；
- 另外 `power log start/dump` 能把电池电压每 30 秒录进 Flash（**拔线也能录**），用来比省电效果。

**⑤ 顺带确认了上一版的省电收益**
你用万用表量出来的 **亮屏 80mA / 息屏 51mA**（省 29mA，约 36%）就是 v0.7.1 那一档的实际效果。

**还没做、建议下一步做的**：
- **第二档省电**（收益最大）：息屏那 51mA 底噪主要来自"CPU 240MHz 双核常开 + 面板"，
  要靠**降频 / 轻睡眠**才能压下去，风险最高，建议单独立项；
- **长按 PWR 关机**：现在要关机只能拔电池（自锁生效后的必然结果），建议下一版补上；
- 另外提醒一个硬件事实：这级电源是 **LDO 不是升降压**，**电池最后一段（约 3.6V 以下）其实用不了** ——
  所以"电量显示还有 40%"时板子已经进入危险区，这只能靠换更大/更低内阻的电芯解决，软件改不了。

*本文档对应固件 v0.7.2 · 2026-10-11*
